# Implementation Plan: Production Foundation Slice

**Branch**: `spec/production-foundation` | **Date**: 2026-08-04 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `/specs/001-production-foundation/spec.md`

**Constitution**: v2.0.0

## Summary

Stand up MyNet as a real product through a **vertical walking skeleton**: an attendee signs in, the
browser calls a project-owned API, the API queries PostgreSQL scoped to that attendee's identity, and
the responsive shell renders who they are and which events they are registered for — across five
individually addressable destinations that carry no content yet.

The technical approach, resolved in [research.md](./research.md): a pnpm workspace holding a
React + TypeScript client on Vite and a Fastify API on Node, over managed PostgreSQL on Neon accessed
through Drizzle with committed SQL migrations. Authentication is self-implemented using opaque
server-side sign-in sessions with Argon2id password hashing, because the spec's own requirements
(server-side revocation, sliding expiry, per-device independence) select that design over stateless
tokens. The API contract is generated from Fastify route schemas by `@fastify/swagger`, committed, and
diff-checked in CI so contract changes surface in review.

The choice that ties the most requirements together is **Neon database branching**: one mechanism
gives per-PR database isolation for previews (FR-067) and clean-database migration verification
(FR-038) at once.

## Technical Context

**Language/Version**: TypeScript across client and API; Node LTS runtime for the API

**Primary Dependencies**: React, Vite, a client router, Tailwind CSS v4, `lucide-react`,
`vite-plugin-pwa` (client); Fastify, `@fastify/swagger`, Drizzle ORM + drizzle-kit, Argon2id (API)

**Storage**: Managed PostgreSQL on Neon. Six tables (see [data-model.md](./data-model.md)). Versioned
SQL migrations generated by drizzle-kit and committed

**Testing**: Vitest (unit, component via React Testing Library, integration via `fastify.inject()`
against a real database); Playwright with `@axe-core/playwright` (end-to-end and accessibility)

**Target Platform**: Installable PWA in current browsers, desktop through mobile; Linux-hosted API
container. No Apple infrastructure anywhere in the pipeline

**Project Type**: Web application — separate client and API in one workspace

**Performance Goals**: Shell initial JavaScript ≤ **200 KB gzipped**, enforced in CI (FR-072).
No latency or throughput target is set; **spec Open Question 21** records that gap deliberately

**Constraints**: No horizontal scrolling at any width from 320px (FR-020) · zero critical or serious
accessibility violations (SC-005) · zero direct platform or network calls in feature code (SC-008) ·
zero colour literals outside the token file (SC-009) · offline shell required, and offline behaviour
must be **bounded and honest** rather than pretending to work (FR-052, FR-053)

**Scale/Scope**: Five destinations with no content · six tables · roughly five endpoints · one actor.
Volume assumptions are not stated and are not needed at this scale

### Source Code (repository root)

```text
apps/
├── web/                      # React + TypeScript client (Vite)
│   ├── src/
│   │   ├── app/              # root, providers, router, five destination routes
│   │   ├── shell/            # nav rail, reduced rail, bottom nav, top bar, not-found
│   │   ├── auth/             # sign-in screen, session-expired handling
│   │   └── theme/            # the single token file — the only place colours exist
│   └── tests/                # component tests (Vitest + Testing Library)
└── api/                      # Fastify + TypeScript API (Node)
    ├── src/
    │   ├── routes/           # route schemas — the contract's source of truth
    │   ├── auth/             # sign-in, sign-out, session validation, throttling
    │   ├── db/               # Drizzle schema and client
    │   └── plugins/          # swagger, auth context binding, error handling
    ├── migrations/           # generated SQL, committed, reviewed
    └── tests/                # integration tests against a real database

packages/
├── platform/                 # six device capability interfaces + web/no-op implementations
├── data/                     # repository interfaces + HTTP implementations
└── config/                   # shared TypeScript, lint, and test configuration

contracts/
└── openapi.json              # generated from route schemas, committed, diff-checked in CI

e2e/                          # Playwright specs, including accessibility checks

.github/workflows/            # CI: eleven gates, Neon branch lifecycle, preview deploys
```

**Structure Decision**: A single repository with pnpm workspaces (research.md D1). `apps/web` and
`apps/api` are separate deployables; `packages/platform` and `packages/data` hold the interfaces
Principle V requires, so the dependency direction is enforced by package boundaries rather than by
convention — feature code in `apps/web/src` depends on `packages/data`, never on transport.

`contracts/openapi.json` sits at the root because both apps relate to it: the API generates it, the
client is verified against it, and CI diffs it.

The single repository is what makes FR-044b's contract check possible in one CI run on one commit.

## Complexity Tracking

> Recorded because the architecture imposes it, not because a principle is violated.

| Item | Why needed | Simpler alternative rejected because |
|---|---|---|
| **Three ephemeral resources per pull request** — a Neon database branch, an ephemeral API deployment, and a Cloudflare Pages preview | FR-034/FR-066 require a preview of *that exact change* a reviewer can open with no local setup, and FR-067 forbids previews touching real attendee data. A client preview is useless without an API, and an API is wrong without the PR's own database — so all three must be per-PR and wired together | **A shared preview API** cannot work: one API instance cannot serve many PRs each expecting its own database branch. **A client-only preview** would render a shell that cannot sign in, failing FR-066's "working preview". **Pointing previews at a long-lived database** directly violates FR-067. This is the operational cost of the owner's choice of a custom API over a managed BaaS, which was made with that cost visible |

**Note for the phase-split decision** (spec Open Question 16): this row is the strongest argument that
the slice is large. Building CI that orchestrates three ephemeral resources is meaningful work sitting
alongside the shell, the schema, and the auth flow in one pull request.

## Open items carried forward

Planning resolved Open Questions 10–14. It could not resolve, and did not touch:

- **Client decisions (1–9)** — identity model, event scoping, connection model, card exchange,
  retention/deletion/export, brand mark, `requirements.md` divergence, "PS", and client validation of
  the desktop and tablet layouts.
- **Open Question 15** — preview access control. Mitigated but not resolved: previews are backed by
  ephemeral seeded databases, so a public preview URL exposes throwaway data rather than real data.
- **Open Questions 18, 19** — residual risks accepted at clarification: no absolute session ceiling,
  and contract changes visible but not classified as breaking.
- **Open Questions 20, 21** — observability baseline and reliability targets, deferred at the
  clarification quota.
- **Open Question 16** — whether this ships as one pull request. See Complexity Tracking.
- **Open Question 17** — server-side branch protection unavailable on a private free-tier repository.

**Flagged for owner confirmation before implementation**: research.md **D8** (self-implemented
authentication). It reads like a reversible library choice but is sticky — it shapes the attendee and
credential tables and every future recovery flow.
